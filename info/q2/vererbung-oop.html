Vererbung, Methodenanpassung & super-Aufrufe

Wie wir Klassenhierarchien mit extends aufbauen, den Unterschied zwischen Überschreiben und Überladen meistern und den super-Aufruf gezielt im Konstruktor sowie in Methoden einsetzen.

1

Das Szenario: Das Mensa-Karten-System der Schule

An unserer Schule nutzen alle Personen eine digitale Mensa-Karte. Jeder Benutzer besitzt gemeinsame Eigenschaften (Name, ID, Guthaben), doch verschiedene Benutzergruppen verhalten sich beim Bezahlen unterschiedlich:

• Oberklasse: Nutzer Allgemeine Basisklasse für alle Mensa-Karten. Speichert name, id und guthaben. Zieht beim Bezahlen den Betrag vom Guthaben ab.
• Unterklasse: Schueler Erbt von Nutzer (extends Nutzer). Speichert zusätzlich die klasse (z. B. "Q2") und erhält automatisch 10% Schülerrabatt beim Bezahlen!
Die Problemstellung ohne Vererbung:
Müssten wir für Schueler und Lehrer jeweils eigene Klassen schreiben, würden wir Attribute wie name, guthaben und Methoden wie guthabenAufladen(...) doppelt programmieren.

Die Lösung durch Vererbung: Die Unterklasse Schueler erbt mit dem Schlüsselwort extends alle Attribute und Methoden der Oberklasse Nutzer und passt nur das an, was speziell ist!
2

Oberklasse Nutzer & Unterklasse Schueler mit super(...)

Schauen wir uns die Oberklasse Nutzer an. Die Attribute sind wie in den Materialien der Abiturkommission NRW mit protected oder private geschützt: 

public class Nutzer {
    private String name;
    private String id;
    protected double guthaben;

    public Nutzer(String pName, String pId, double pGuthaben) {
        this.name = pName;
        this.id = pId;
        this.guthaben = pGuthaben;
    }

    public void bezahlen(double pBetrag) {
        if (this.guthaben >= pBetrag) {
            this.guthaben -= pBetrag;
        }
    }
}

Der super(...)-Aufruf im Konstruktor der Unterklasse

Da die Attribute name und id in der Oberklasse private sind, kann die Unterklasse Schueler nicht direkt darauf zugreifen. Sie ruft deshalb in der allerersten Zeile ihrem Konstruktor den Oberklassen-Konstruktor mit super(...) auf: 

public class Schueler extends Nutzer {
    private String klasse;

    public Schueler(String pName, String pId, double pGuthaben, String pKlasse) {
        super(pName, pId, pGuthaben); // 1. WICHTIG: Erster Aufruf initialisiert Oberklasse!
        this.klasse = pKlasse;        // 2. Eigenes Attribut initialisieren
    }
}
3

Überschreiben vs. Überladen (Der zentrale Unterschied)

In Klausuren wird oft verwechselt, was Überschreiben (Overriding) und was Überladen (Overloading) bedeutet. Hier ist die Gegenüberstellung:

Methoden ÜBERSCHREIBEN (Overriding) Methoden ÜBERLADEN (Overloading)
• Wo? In der Unterklasse (vererbungsspezifisch).
• Signatur: Exakt gleicher Name und exakt gleiche Parameterliste wie in der Oberklasse.
• Zweck: Die Unterklasse ersetzt oder spezialisiert das Verhalten der Oberklasse.
• Annotation: Best Practice mit @Override. 		• Wo? In der gleichen Klasse oder auch in Unterklassen.
• Signatur: Gleicher Name, aber UNTERSCHIEDLICHE Parameterliste (Anzahl oder Typen der Parameter).
• Zweck: Bietet dem Aufrufer verschiedene Wege an, eine Methode zu nutzen (z. B. mit oder ohne Zusatzangabe).

1. Beispielfall: Überschreiben mit super.bezahlen(...)

Ein Schüler bekommt 10% Rabatt. Wir überschreiben die Methode bezahlen(double pBetrag) und nutzen super.bezahlen(...), um den bereits fertig abgebuchten Vorgang der Oberklasse nicht neu schreiben zu müssen: 

    @Override
    public void bezahlen(double pBetrag) {
        double rabattierterBetrag = pBetrag * 0.90; // 10% Schuelerrabatt
        super.bezahlen(rabattierterBetrag);          // Ruft die Abbuchungslogik der Oberklasse auf!
    }

2. Beispielfall: Überladen von bezahlen(...)

Zusätzlich bieten wir in der Klasse eine **überladene** Methode an, die neben dem Betrag auch noch den Artikelnamen als Protokoll entgegennimmt: 

    // Überladene Methode (unterschiedliche Parameterliste!)
    public void bezahlen(double pBetrag, String pArtikelName) {
        System.out.println("Kauf von: " + pArtikelName);
        this.bezahlen(pBetrag); // Ruft die normale bezahlen-Methode auf
    }
MERKE
Vererbung, super & Methodensignaturen in Java:

1. super(...) im Konstruktor: Muss die allererste Anweisung im Konstruktor der Unterklasse sein, um die Attribute der Oberklasse zu initialisieren.

2. super.methode(...) bei Methoden: Greift gezielt auf die Methode der Oberklasse zu, falls die Unterklasse diese Methode mit @Override überschrieben hat.

3. Überschreiben (Overriding): Unterklasse nutzt exakt dieselbe Signatur (Name + Parameter) wie die Oberklasse, um deren Verhalten zu spezialisieren.

4. Überladen (Overloading): Methoden heißen gleich, unterscheiden sich aber in ihren Parametern (Typen oder Anzahl). Der Compiler wählt anhand der Argumente die passende Methode aus.

Detektiv-Check: Quelltext-Analyse & Typische Fehler

Analysiere die Quelltexte und teste dein Verständnis. Klicke auf die Buttons, um die Erklärungen aufzudecken.

1. Frage: Warum meldet der Java-Compiler einen Fehler, wenn super(pName, pId, pGuthaben) an zweiter Stelle im Konstruktor steht?
• Regel: Java schreibt vor, dass die Oberklasse vollständig konstruiert sein muss, bevor die Unterklasse eigene Attribute initialisiert.
• Erklärung: Würde erst eigener Code ausgeführt, könnte dieser versehentlich auf noch uninitialisierte Attribute der Oberklasse zugreifen. Deshalb muss super(...) zwingend in der allerersten Zeile stehen.
2. Frage: Liegt in folgendem Code ein Überschreiben oder ein Überladen vor?
Oberklasse: void drucken(int pAnzahl)
Unterklasse: void drucken(String pText)
• Antwort: Es handelt sich um Überladen!
• Begründung: Obwohl die Methode in einer Unterklasse definiert ist, unterscheidet sich der Parametertyp (int vs. String). Es ist somit eine neue, überladene Variante der Methode und kein Überschreiben!
3. Frage: Was passiert, wenn man in Schueler.bezahlen(...) aus Versehen bezahlen(rabattierterBetrag) statt super.bezahlen(...) schreibt?
• Folge: Es entsteht eine endlose Rekursion (StackOverflowError)!
• Erklärung: Ohne das Schlüsselwort super. ruft die Methode bezahlen sich selbst immer wieder in der Unterklasse auf, anstatt die Abbuchung der Oberklasse auszuführen.
