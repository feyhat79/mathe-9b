Vererbung, Überschreiben & Überladen

Vom Albtraum doppelten Quellcodes zur eleganten Klassenhierarchie mit extends. Wir meistern das Fundament-Prinzip mit super(...) und den zentralen Unterschied zwischen Methoden-Überschreiben und Methoden-Überladen.

Einstieg: Das Rollenspiel-Dilemma (Warum Vererbung?)

Stell dir vor, du entwickelst die Logik für ein rundenbasiertes Rollenspiel. Im Spiel treten verschiedene Charaktere an: tapfere Krieger mit schwerer Eisenrüstung und weise Magier mit mächtigen Zaubersprüchen.

Das Albtraumszenario OHNE Vererbung (Copy-&-Paste-Programmierung):
Schreiben wir für Krieger und Magier jeweils eine völlig eigenständige Klasse, müssen wir Attribute wie name, lebenspunkte, basisSchaden und Methoden wie nimmSchaden() oder heilen() in beiden Klassen doppelt programmieren.

Die gravierende Folge: Ändert sich eine grundlegende Spielregel (z. B. „Lebenspunkte dürfen nach einem Treffer niemals negativ werden, sondern stoppen bei 0“), müssen wir jede Klasse einzeln suchen und manuell umschreiben. Wer das vergisst, erzeugt inkonsistente Bugs. In der Software-Entwicklung verstößt dies gegen das fundamentale Prinzip DRY (Don't Repeat Yourself).

Die architektonische Lösung: Generalisierung & Spezialisierung

Wir analysieren alle Figuren und trennen das Gemeinsame vom Besonderen:

• Oberklasse: Spielfigur Bündelt alle universellen Eigenschaften: Name, Lebenspunkte, Basisschaden sowie Standard-Aktionen wie Schaden nehmen, Heilen und Statusanzeige.
• Unterklasse: Krieger Erbt alles von Spielfigur. Besitzt zusätzlich eine ruestung, die erlittenen Schaden vorab absorbiert.
• Unterklasse: Magier Erbt alles von Spielfigur. Besitzt zusätzlich mana und feuert mächtige Zauberangriffe mit doppeltem Schaden ab.
Die „Ist-ein“-Beziehung (Generalisierung):
Vererbung modelliert immer eine hierarchische Beziehung:
  • Ein Krieger ist eine Spielfigur.
  • Ein Magier ist eine Spielfigur.
In Java wird diese Beziehung mit dem Schlüsselwort extends ausgedrückt.

Die Implementierung: Sichtbarkeit & das Fundament mit super(...)

1. Die Oberklasse: Spielfigur.java

Attribute werden als protected deklariert. Dadurch sind sie für die eigenen Methoden und alle erbenden Unterklassen direkt erreichbar, bleiben aber nach außen hin vor fremden Zugriffen gekapselt: 

public class Spielfigur {
    // protected: Sichtbar in dieser Klasse UND in allen erbenden Unterklassen
    protected String name;
    protected int lebenspunkte;
    protected int basisSchaden;

    public Spielfigur(String pName, int pLebenspunkte, int pBasisSchaden) {
        this.name = pName;
        this.lebenspunkte = Math.max(0, pLebenspunkte);
        this.basisSchaden = Math.max(0, pBasisSchaden);
    }

    public void nimmSchaden(int pSchaden) {
        if (pSchaden > 0) {
            this.lebenspunkte -= pSchaden;
            if (this.lebenspunkte < 0) {
                this.lebenspunkte = 0;
            }
            System.out.println("[" + this.name + "] erleidet " + pSchaden + " Schaden. LP: " + this.lebenspunkte);
        }
    }

    public void angreifen(Spielfigur pZiel) {
        if (pZiel == null) {
            System.out.println("Kein gueltiges Ziel angegeben!");
        } else if (!istLebendig()) {
            System.out.println("[" + this.name + "] kann nicht angreifen, da kampfunfaehig.");
        } else {
            System.out.println("[" + this.name + "] fuehrt Basisangriff auf [" + pZiel.getName() + "] aus (" + this.basisSchaden + " Schaden).");
            pZiel.nimmSchaden(this.basisSchaden);
        }
    }
}

2. Der Konstruktor der Unterklasse: Das Fundament-Prinzip

Wenn wir ein Objekt vom Typ Krieger instanziieren, muss im Arbeitsspeicher zuerst das Basis-Objekt der Spielfigur existieren. Daher verlangt die Java-Sprachspezifikation verbindlich:

Die Fundament-Regel: Der Aufruf des Oberklassen-Konstruktors mit super(...) muss ausnahmslos die allererste Anweisung im Konstruktor der Unterklasse sein! Erst wenn das Fundament steht, dürfen spezifische Unterklassen-Attribute initialisiert werden. 
public class Krieger extends Spielfigur {
    // protected: Erlaubt zusaetzlich spaeteren Spezialisierungen (z. B. Paladin) direkten Zugriff
    protected int ruestung;

    public Krieger(String pName, int pLebenspunkte, int pBasisSchaden, int pRuestung) {
        super(pName, pLebenspunkte, pBasisSchaden); // 1. ZWINGEND ERSTE ZEILE: Initialisiert Spielfigur
        this.ruestung = Math.max(0, pRuestung);     // 2. Eigenes Attribut des Kriegers setzen
    }
}

Überschreiben (Overriding) vs. Überladen (Overloading)

In Informatik-Klausuren und im Abitur gehören die Begriffe Überschreiben und Überladen zu den häufigsten Fehlerquellen. Sie klingen ähnlich, beschreiben aber zwei völlig unterschiedliche Konzepte der objektorientierten Programmierung:

Methoden ÜBERSCHREIBEN (Method Overriding) Methoden ÜBERLADEN (Method Overloading)
• Wo? Ausschließlich zwischen Ober- und Unterklasse (setzt Vererbung voraus).

• Signatur: Exakt derselbe Name und exakt dieselbe Parameterliste (Anzahl und Typen).

• Zweck: Die Unterklasse spezialisiert oder verändert das Verhalten einer geerbten Methode.

• Kennzeichnung: Empfohlen mit @Override. Der Compiler prüft, ob die Methode in der Oberklasse wirklich existiert.

• Bindungszeitpunkt: Dynamische Methodenbindung zur Laufzeit (Polymorphie). 		• Wo? Innerhalb derselben Klasse (oder auch über Vererbungsgrenzen hinweg).

• Signatur: Derselbe Name, aber UNTERSCHIEDLICHE Parameterliste (andere Anzahl oder andere Datentypen).

• Zweck: Bietet dem Aufrufer unterschiedliche Bedienvarianten derselben Aktion an (z. B. Standardwert vs. Detailkonfiguration).

• Kennzeichnung: Keine besondere Annotation.

• Bindungszeitpunkt: Statische Bindung bereits beim Kompilieren anhand der übergebenen Parameter.

1. Praxisbeispiel: Überschreiben mit super.methode(...)

Der Krieger überschreibt die Methode nimmSchaden(int pSchaden). Seine Rüstung fängt Schaden ab. Anschließend ruft er mit super.nimmSchaden(...) die Basismethode der Oberklasse auf, damit die Lebenspunkte an zentraler Stelle abgezogen werden: 

// In der Klasse Krieger:
@Override
public void nimmSchaden(int pSchaden) {
    int effektiverSchaden = pSchaden - this.ruestung;
    if (effektiverSchaden < 0) {
        effektiverSchaden = 0;
    }
    System.out.println("[" + this.name + "] blockt mit Ruestung. Schaden reduziert auf: " + effektiverSchaden);
    
    // Weiterleitung an die Oberklasse Spielfigur:
    super.nimmSchaden(effektiverSchaden);
}

2. Praxisbeispiel: Überladen der Methode angreifen(...)

In der Oberklasse Spielfigur stellen wir zwei Varianten von angreifen bereit: einen einfachen Angriff und einen Kraftangriff mit Bonus-Schaden: 

// Variante 1: Normaler Angriff (1 Parameter)
public void angreifen(Spielfigur pZiel) {
    pZiel.nimmSchaden(this.basisSchaden);
}

// Variante 2: UEBERLADENE Methode mit Bonusschaden (2 Parameter!)
public void angreifen(Spielfigur pZiel, int pBonusSchaden) {
    int gesamt = this.basisSchaden + Math.max(0, pBonusSchaden);
    System.out.println("[" + this.name + "] fuehrt Kraftangriff aus!");
    pZiel.nimmSchaden(gesamt);
}
MERKE
Die 4 goldenen Regeln der Vererbung in Java:

1. Klassenhierarchie mit extends: Die Unterklasse erbt alle nicht-privaten Attribute und Methoden der Oberklasse. Sie erweitert oder spezialisiert das Verhalten („Ist-ein“-Beziehung).

2. Fundament-Regel mit super(...): Der Konstruktor der Oberklasse muss als allererste Zeile im Unterklassen-Konstruktor aufgerufen werden. Erst danach dürfen eigene Attribute initialisiert werden.

3. Überschreiben (Overriding): Exakt gleiche Signatur (gleicher Name, identische Parameterliste) in der Unterklasse. Spezialisiert das geerbte Verhalten. Mit super.methode() kann die ursprüngliche Logik der Oberklasse weiterverwendet werden.

4. Überladen (Overloading): Gleicher Name, aber unterschiedliche Parameterliste. Kann innerhalb derselben Klasse existieren. Der Compiler entscheidet beim Übersetzen anhand der Argumente, welche Variante aufgerufen wird.

Detektiv-Check: Klausurtypische Verständnisfragen

Teste dein Verständnis der Konzepte an diesen typischen Fragestellungen. Klicke auf die Schaltfläche, um die ausführliche Begründung aufzudecken.

1. Frage: Warum meldet der Java-Compiler einen Fehler, wenn super(pName, pLP, pSchaden) erst nach this.ruestung = pRuestung steht?
• Regel: Java verlangt, dass die Basisklasse vollständig konstruiert sein muss, bevor die Unterklasse eigene Initialisierungen vornimmt.
• Erklärung: Würde vor dem super(...)-Aufruf eigener Code ausgeführt, könnte dieser auf Methoden oder Felder der Oberklasse zugreifen, die zu diesem Zeitpunkt noch gar nicht initialisiert wurden. Deshalb erzwingt der Compiler, dass super(...) zwingend an erster Stelle steht.
2. Frage: Liegt in folgendem Methodenpaar ein Überschreiben oder ein Überladen vor?
Oberklasse: void heilen(int pPunkte)
Unterklasse: void heilen(Spielfigur pZiel, int pPunkte)
• Antwort: Es handelt sich um Überladen (Overloading)!
• Begründung: Obwohl sich die zweite Methode in der Unterklasse befindet, hat sie eine andere Parameterliste (zwei Parameter statt einem). Die ursprüngliche Methode heilen(int) bleibt in der Unterklasse weiterhin unverändert erhalten. Die Unterklasse bietet lediglich eine zusätzliche, überladene Variante an.
3. Frage: Was passiert zur Laufzeit, wenn man in Krieger.nimmSchaden(...) versehentlich nimmSchaden(effektiverSchaden) statt super.nimmSchaden(effektiverSchaden) aufruft?
• Folge: Das Programm stürzt mit einem java.lang.StackOverflowError ab!
• Erklärung: Ohne das Präfix super. ruft sich die Methode der Unterklasse selbst unendlich oft rekursiv auf. Erst durch super.nimmSchaden(...) wird gezielt die Implementierung der Oberklasse adressiert.
4. Frage: Warum nutzt die Oberklasse für Attribute wie name und lebenspunkte das Schlüsselwort protected anstelle von private?
• Antwort: Bei private haben selbst erbende Unterklassen keinen direkten Lese- oder Schreibzugriff auf das Attribut.
• Erklärung: Mit protected dürfen spezialisierte Klassen wie Krieger oder Magier direkt auf this.name oder this.lebenspunkte zugreifen (z. B. für Bildschirmausgaben), während fremde Klassen von außerhalb keinen direkten Zugriff erhalten.

Aufgabe 2: Implementierung (Überschreiben)

Krieger-Spezialisierung: Kritischer Schild-Block

Erweitere in der Klasse Krieger die überschriebene Methode nimmSchaden(int pSchaden):
Wenn der erlittene Schaden höher als 30 Punkte ist, aktiviert der Krieger automatisch einen Notfall-Schildwall, der die Rüstung für diesen Treffer verdoppelt!

Musterlösung für Aufgabe 2 aufdecken
@Override
public void nimmSchaden(int pSchaden) {
    int wirksameRuestung = this.ruestung;
    if (pSchaden > 30) {
        wirksameRuestung = this.ruestung * 2;
        System.out.println("[" + this.name + "] aktiviert Notfall-Schildwall! Ruestung verdoppelt auf " + wirksameRuestung);
    }
    int effektiverSchaden = Math.max(0, pSchaden - wirksameRuestung);
    super.nimmSchaden(effektiverSchaden);
}
Aufgabe 3: Implementierung (Überladen)

Magier-Erweiterung: Zauberangriff mit Elementar-Wahl

Der Magier besitzt bereits angreifen(Spielfigur pZiel).
Füge in Magier.java eine überladene Methode angreifen(Spielfigur pZiel, String pElement) hinzu:
• Kostet 15 Mana.
• Richtet 3-fachen Basisschaden an.
• Gibt den Elementtyp (z. B. "Eis" oder "Blitz") im Terminal aus.

Musterlösung für Aufgabe 3 aufdecken
// UEBERLADENE METHODE: Gleicher Name, zusaetzlicher Parameter String pElement
public void angreifen(Spielfigur pZiel, String pElement) {
    if (pZiel == null || !istLebendig()) {
        return;
    }
    if (this.mana >= 15) {
        this.mana -= 15;
        int elementarSchaden = this.basisSchaden * 3;
        System.out.println("[" + this.name + "] schleudert einen " + pElement + "-Sturm auf [" 
                           + pZiel.getName() + "]! (" + elementarSchaden + " Schaden, Rest-Mana: " + this.mana + ")");
        pZiel.nimmSchaden(elementarSchaden);
    } else {
        System.out.println("Zu wenig Mana fuer Elementarzauber! Nutzt Basis-Angriff.");
        this.angreifen(pZiel); // Ruft die regulaere angreifen-Methode auf
    }
}

Neue Klasse: Bogenschütze

Entwirf im Kopf oder auf Papier den Bauplan für eine dritte Unterklasse Bogenschuetze extends Spielfigur.
Welches zusätzliche Attribut benötigt er? Wie muss sein Konstruktor aussehen? Welche Methode sollte er überschreiben?

Architektur-Skizze aufdecken
• Zusätzliches Attribut: private int pfeile; (z. B. Startwert 20 Pfeile).
• Konstruktor: Ruft in Zeile 1 super(pName, pLebenspunkte, pBasisSchaden); auf und setzt anschließend this.pfeile = pPfeile;.

• Spezifische Methode: public void koecherAuffuellen(int anzahl).

Stufe 2: Mehrstufige Vererbung (Programmier-Mission: Eismagier)

Bisher haben wir eine flache Hierarchie betrachtet: Krieger und Magier erben direkt von Spielfigur. In größeren Softwaresystemen spezialisieren sich Klassen jedoch über mehrere Ebenen hinweg. Genau das bezeichnet man als mehrstufige Vererbung.

Die Vererbungskette (Transitivität):
Spielfigur (Wurzel)  ➔  Magier (1. Spezialisierung)  ➔  Eismagier (2. Spezialisierung)
• Ein Eismagier ist ein Magier.
• Weil jeder Magier eine Spielfigur ist, ist ein Eismagier automatisch auch eine Spielfigur! Er erbt alle Attribute und Methoden beider Vorgängerklassen (Name, Lebenspunkte, Basisschaden, Mana, Heilen, Meditieren etc.).

Die Fundament-Kaskade im Konstruktor:

Wenn der Konstruktor von Eismagier aufgerufen wird, ruft er in Zeile 1 mit super(...) den Konstruktor von Magier auf. Dieser ruft wiederum in Zeile 1 mit super(...) die Spielfigur auf.

Erst wenn das gesamte Fundament von oben nach unten gegossen ist, initialisiert jede Stufe ihre eigenen Attribute.

Vollständige Musterlösung für Eismagier.java aufdecken
/**
 * Unterklasse Eismagier
 * 
 * Demonstriert mehrstufige Vererbung:
 * Spielfigur -> Magier -> Eismagier
 */
public class Eismagier extends Magier {
    // Spezifisches Attribut der 3. Generation
    private int frostGrad;

    public Eismagier(String pName, int pLebenspunkte, int pBasisSchaden, int pMana, int pFrostGrad) {
        // 1. Ruft den Konstruktor von Magier auf (dieser ruft Spielfigur auf)
        super(pName, pLebenspunkte, pBasisSchaden, pMana);
        // 2. Eigenes Attribut initialisieren
        this.frostGrad = Math.max(1, pFrostGrad);
    }

    @Override
    public void angreifen(Spielfigur pZiel) {
        if (pZiel == null) {
            System.out.println("Kein gueltiges Ziel angegeben!");
        } else if (!istLebendig()) {
            System.out.println("[" + this.name + "] kann nicht angreifen, da kampfunfaehig.");
        } else if (this.mana >= 12) {
            this.mana -= 12;
            int frostSchaden = (this.basisSchaden * 2) + (this.frostGrad * 3);
            System.out.println("[" + this.name + "] entfesselt einen Blizzard auf [" + pZiel.getName() 
                               + "]! (-12 Mana, Frostgrad " + this.frostGrad + ", " + frostSchaden + " Schaden, Rest-Mana: " + this.mana + ")");
            pZiel.nimmSchaden(frostSchaden);
        } else {
            System.out.println("[" + this.name + "] hat nicht genug Mana fuer Blizzard (nur " + this.mana + " Mana). Greift normal an!");
            // Ruft die angreifen-Methode der direkten Oberklasse Magier auf:
            super.angreifen(pZiel);
        }
    }

    // Spezifische Methode des Eismagiers
    public void eispanzer() {
        System.out.println("[" + this.name + "] huellt sich in einen schuetzenden Eispanzer!");
        this.heilen(15);
    }

    @Override
    public void statusAusgeben() {
        super.statusAusgeben(); // Gibt Name, LP, Schaden und Mana via Magier/Spielfigur aus
        System.out.println("Frostgrad:    " + this.frostGrad);
    }

    public int getFrostGrad() {
        return this.frostGrad;
    }
}
